# ADR-0001 · Layer 1 스캐너 실행 환경

- 상태: **채택**
- 일자: 2026-09-05
- 관련: `SDD.md` §2·§3·§7 · `AGENTS.md` INV-5

## 맥락

Layer 1은 매주 250여 개 도메인에 대해 `robots.txt` · 홈 · sitemap · TLS를 점검한다. 2026-09-05 예비 실측(`K09`)에서 확인된 사실이 선택을 제약한다.

- **일부 도메인은 응답하지 않는다.** 9곳 중 2곳이 연결 시간 초과였다. 타임아웃은 예외가 아니라 상시 상태이므로, 재시도와 백오프가 설계에 내장돼야 한다.
- **한 도메인당 최대 4회의 순차 요청**이 필요하고, 같은 호스트에 대해 최소 간격을 지켜야 한다(예의 있는 수집). 즉 전수 1회는 **본질적으로 느린 작업**이다.
- 그러나 **동시성은 자유롭게 올릴 수 없다.** 공공 서버에 부하를 주지 않는 것이 이 제품의 정당성 조건이다.

후보는 셋이었다.

1. Supabase Edge Functions + `pg_cron`
2. Vercel Cron + Route Handler
3. 별도 Node 워커 (Fly.io · Railway 등)

## 결정

**Supabase Edge Functions + `pg_cron` + Postgres 큐**를 채택한다.

배포 대상 서비스를 **Vercel과 Supabase 둘**로 유지한다. 세 번째 인프라를 추가하려면 새 ADR을 쓴다.

## 근거

핵심은 **실행 시간 제한을 설계 제약이 아니라 배치 크기 파라미터로 바꾸는 것**이다.

전수 스캔이 한 번의 함수 호출 안에서 끝나야 한다면 실행 시간 제한이 치명적이다. 그러나 작업을 Postgres 큐에 넣고 워커를 짧게 여러 번 깨우면, **한 호출이 얼마나 오래 사는가는 중요하지 않다.** 각 호출은 `claim_scan_jobs(20)` 로 소량만 가져가 처리하고 끝난다. 남은 일은 다음 호출이 이어받는다. 6시간 동안 2분마다 깨우면 180회 × 20건 = 3,600건 처리 여력이 있어, 250여 도메인에 재시도를 얹어도 충분하다.

큐를 DB에 두면 부수적 이득이 크다.

- `unique (domain_id, scheduled_week)` 로 **도메인당 주 1회를 DB가 보장**한다. 애플리케이션 로직의 실수로 같은 서버를 두 번 두드리는 일이 구조적으로 불가능하다.
- `FOR UPDATE SKIP LOCKED` 로 워커를 몇 개 띄우든 중복 처리가 없다.
- 실패·재시도·리스 만료가 전부 행으로 남아 운영 대시보드가 공짜로 나온다.

**Vercel Cron을 택하지 않은 이유** — 서버리스 실행 시간이 더 짧아 배치를 더 잘게 쪼개야 하고, 무엇보다 스캔 트래픽이 웹 요청 처리와 같은 런타임을 공유하게 된다. 공개 페이지 응답성과 스캔 부하를 같은 곳에 두는 것은 피하고 싶다. 큐 상태도 결국 Supabase에 두게 되므로, 호출자만 Vercel로 옮기는 것에 실익이 없다.

**별도 워커를 택하지 않은 이유** — 기술적으로는 가장 자유롭다. 장시간 실행, 정교한 동시성 제어, 요청 간격의 정밀한 조율이 가능하다. 그러나 이 제품의 스캔은 **의도적으로 느리게** 돌아간다. 속도가 병목이 아니라 예의가 제약이다. 자유도를 살릴 곳이 없는데 유지할 서비스와 비용만 늘어난다. MVP 단계에서 인프라 하나를 줄이는 편익이 더 크다.

## 결과

**좋아지는 것**

- 인프라가 둘뿐이다. 배포·비밀·모니터링 경로가 단순하다.
- 큐가 DB에 있어 관측성이 높고, 스캔 이력이 곧 운영 데이터다.
- 워커 확장이 `pg_cron` 주기 조정만으로 끝난다.

**나빠지는 것 / 감수하는 것**

- 한 함수 호출 안에서 긴 순차 작업을 할 수 없다. **모든 스캔 로직은 재개 가능해야 한다** — 도메인 하나의 처리가 원자적이어야 하고, 중간 상태를 메모리에 두면 안 된다.
- `pg_cron` 은 UTC로 동작한다. 스케줄을 KST로 적으면 반드시 한 번은 틀린다. 모든 스케줄은 UTC로 적고 KST를 주석으로 단다.
- Edge Function 런타임은 Deno다. Next.js 쪽 스캐너 유틸을 그대로 공유할 수 없는 경우가 생긴다. 판정 로직은 **런타임 의존이 없는 순수 함수**로 분리해 양쪽에서 쓴다.

## 되돌리는 조건

다음 중 하나가 발생하면 별도 워커(후보 3)로 재검토한다.

- 전수 1회가 6시간 안에 끝나지 않는다(NFR-1 위반).
- Layer 3 측정이 커져 AI API 호출의 장시간 스트리밍·재시도가 필요해진다.
- 산하 기관 확대(v2)로 대상 도메인이 1,000개를 넘는다.
